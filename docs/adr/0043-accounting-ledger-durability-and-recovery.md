# Accounting-ledger durability: current-state rows, one atomic write, and a restart that refuses rather than guesses

_Accepted via the D10 grilling session on decision ticket [#137](https://github.com/MarcosACH/tickwright/issues/137), part of the trade-economics map [#107](https://github.com/MarcosACH/tickwright/issues/107). Delivers the schema, write cadence and restart sequence ADR-0034 deferred to "the durability ticket". **Extends ADR-0019** (the store's minimal holdings gain the ledger tables), **ADR-0024** (the startup sequence gains a step, and the barrier gains a live-only sub-step), **ADR-0035** (the Tier-1 write is one atomic call, not two), **ADR-0038** (`AccountSpec` gains `genesis_collateral`) and **ADR-0042** (the startup check gains a second condition and a named carrier for the configured genesis). **Resolves ADR-0041 §7's deferred recovery trading-gate**: there is none. **Splits ADR-0037's no-watermark claim by path** — confirmed for paper's catch-up, and made durable on live, where the ingress re-delivers across a restart. **Unchanged by [ADR-0046](./0046-account-abstraction-mode-and-account-grain-sources.md), with a precondition now named**: the live-only boot `clearinghouseState` account materialisation is correct only where that response is the account rather than a perps sub-ledger — Manual/Standard mode, verified at boot by ADR-0046 §3 **before** this ADR's recovery sequence reaches the materialisation step._

ADR-0034 made the `Store` system-of-record for the Tier-1 ledger and for the per-strategy attribution a venue snapshot cannot reconstruct, then deferred the schema. ADR-0035 said Tier-1 is written store-first on the fill-apply path, before publish. ADR-0042 fixed what a paper account opens at. What was left is the part that decides whether any of it survives a crash: what the rows are, whether the writes are atomic, what happens between process start and the first reconcile, and what the engine does when it opens a store that is not the ledger it expects.

## 1. Current-state rows, not an event log

The ledger persists as **mutable current-state rows** — one per position, one per account, one per symbol's funding watermark (§5.2), all upserted in place. Recovery is a `SELECT`. **"Snapshot" means the current row state**, and nothing else: there is no periodic snapshotting job, no separate snapshot table, and no fold-over-history at startup. ADR-0034's use of the word is hereby pinned to this meaning.

This is ADR-0009's decision applied one layer over, and the argument transfers unchanged: the store answers *what is true now*, event-sourced replay was rejected as the live recovery path, and orders already work this way — the `history` column exists but is "an adapter-only audit surface, not part of what recovery reads". **(Amended in the implementing slice ([#172](https://github.com/MarcosACH/tickwright/issues/172)): `history` is no longer *adapter-only* — it is declared on the `Store` Protocol, because eleven engine assertions read the trail to establish what a saga did, and a seam that disclaims its own test surface is one a conforming implementation cannot be swapped into. The half this paragraph rests on is unchanged and is the only half it needs: the trail is still an audit surface and still **not part of what recovery reads**, so nothing folds a log at startup and there is still one recovery model.**)** Persisting an accrual log and folding it at startup would put a **second recovery model** in one engine — fold-the-log for money, read-the-row for orders — which is the outcome ADR-0009's rejection exists to prevent.

**An append-only ledger line-item log is a named extension point, deliberately not taken.** ADR-0009's Consequences already reserve "an optional durable event-capture/audit capability … it never becomes the live recovery path in v1", and a per-fill/per-accrual ledger log is that capability at accounting grain. Adding it later is **purely additive**: a new table, one `INSERT` inside the transaction §4 establishes, one read method — and crucially it has a single write site to be added at, because ADR-0035 already funnels fills, funding and reconcile heals through one synchronous path. What cannot be recovered later is **retroactivity**: the current-state row is a sum, not a trail, so a log added in month seven has history from month seven. That cost is accepted; the alternative was carrying a growth-and-retention surface in v1 for a capability with no reader yet.

## 2. The unattributed partition is a sentinel, not a `NULL`

ADR-0038 reserves `strategy_id: str | None` with `None` as the unattributed partition. **On disk that column is `NOT NULL` and the partition is the reserved literal `__unattributed__`**, translated `None ↔ sentinel` at the adapter boundary — in the `_records.py` peer that exists precisely so the two backends cannot drift on what a row *is*.

A literal `NULL` in the key is not merely awkward, it is **differently broken on each backend**, and one of the breakages is silent on the default path:

- **SQLite** accepts duplicate rows under `PRIMARY KEY (strategy_id, symbol)` when `strategy_id` is `NULL`, and an upsert against that key **inserts another row rather than updating** — the unattributed partition would accrete a new row per heal, unbounded, with the Σ-invariant quietly counting all of them.
- **Postgres** forces primary-key columns `NOT NULL` and **rejects the row** outright.

`UNIQUE` in place of `PRIMARY KEY` does not rescue it: both treat nulls as distinct, so the duplicates return. Postgres offers `UNIQUE NULLS NOT DISTINCT`; SQLite has no equivalent, so that route would break ADR-0019's parity promise at the *default* backend — the one the zero-setup path runs on.

**Rejected: real `NULL` plus a surrogate key and two partial unique indexes** (`UNIQUE(strategy_id, symbol) WHERE strategy_id IS NOT NULL`, `UNIQUE(symbol) WHERE strategy_id IS NULL`). It does enforce correctly on both backends, but the conflict target of an upsert must repeat the partial index's `WHERE` clause, so every ledger write forks into two SQL statements selected on `strategy_id is None`. That is a permanent branch in the hottest, most correctness-critical write in the system, bought to keep a `NULL` on disk that no reader wants.

**Rejected: a separate table for the partition.** It duplicates every column and forks every read and every Σ.

**The sentinel is made uncollidable, not merely conventional.** `strategy_id` is unvalidated today — a plain `str` on `StrategyConfig`, with `StrategyHost.register` checking only for duplicates — so a strategy legitimately named `__unattributed__` would silently merge its ledger with foreign flow. A validator on **both** `StrategyConfig` and `StrategyHost.register` rejects the reserved literal. This mirrors ADR-0042 §5's reasoning in the other direction (a hyphen forbidden in `account_label` so `paper-<label>` stays two segments): reserve exactly what must be reserved. A full naming *grammar* for strategy ids — forcing every id into a shape the sentinel provably cannot take — was rejected as a larger imposition on every existing strategy for the same guarantee.

## 3. The tables

Three tables, added to the three ADR-0019 lists.

```sql
CREATE TABLE IF NOT EXISTS positions (
    strategy_id         TEXT NOT NULL,   -- '__unattributed__' for the reserved partition (§2)
    symbol              TEXT NOT NULL,
    signed_size         TEXT NOT NULL,
    entry_price         TEXT,            -- NULL when flat (ADR-0041 §3)
    realized_pnl        TEXT NOT NULL,
    fees                TEXT NOT NULL,
    funding             TEXT NOT NULL,
    isolated_collateral TEXT,            -- NULL when the position is cross-margined
    ts_ns               INTEGER NOT NULL,
    PRIMARY KEY (strategy_id, symbol)
);

CREATE TABLE IF NOT EXISTS account (
    id                 INTEGER PRIMARY KEY CHECK (id = 1),
    account_id         TEXT NOT NULL,
    genesis_collateral TEXT NOT NULL,
    genesis_ts_ns      INTEGER NOT NULL,   -- written once, with the row; never updated
    cash               TEXT NOT NULL,
    ts_ns              INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS funding_marks (
    symbol             TEXT PRIMARY KEY,
    last_funding_ts_ns INTEGER NOT NULL,   -- the durable funding watermark (§5.2)
    ts_ns              INTEGER NOT NULL
);
```

**`account` is a single row, by constraint.** ADR-0038 makes one-account-per-process a *deployment fact*; `CHECK (id = 1)` encodes it in the schema instead of merely documenting it, exactly as the existing `kill_switch` table does. The §10 mismatch check then reduces to "read the one row and compare", with no ambiguity about *which* row binds the ledger. A table keyed by `account_id` would let one store silently accumulate two account histories — the precise failure ADR-0038's exclusivity invariant exists to prevent.

**`account_id` is therefore stamped once, on the account row — not on every position row.** ADR-0038 reads `account_id` as stamped on "durable ledger rows", and taken literally that means a repeated column on `positions`. The single-row `account` table makes the repetition redundant *and* unsafe: a per-row copy is a second place the binding can be written, so it can disagree with the one row §10 actually checks, and no query needs it — the store holds exactly one account's ledger by construction, so a position row has nothing to be disambiguated from. ADR-0038 is annotated in place accordingly. `account_id` keeps its stamp everywhere it is genuinely a discriminator: on the `FundingAccrual` event (ADR-0037) and on telemetry (ADR-0020), both of which travel outside the store.

**`genesis_collateral` is `NOT NULL` and carries no `CHECK`.** ADR-0042 §6 is explicit that positivity is a validator on paper *config input*, never a column constraint: an unfunded live wallet opens at `accountValue − Σ unrealized_pnl = 0`, and a `CHECK (genesis_collateral > 0)` would reject the exact row that ADR is instructing this schema to write.

**`ts_ns` is the last-write stamp on all three tables, and that is why `account` carries a second one.** Every ledger row is upserted in place (§1), so `ts_ns` says when that row last moved — and on the account row the first fill to move `cash` overwrites it. ADR-0042 §6 populates the genesis column on live specifically so that "when did this ledger open, and at what value" stays answerable, and the value half alone does not answer it. `genesis_ts_ns` is written once, with the row, and never updated. This is §1's retroactivity argument in the other direction: a sum can be recomputed from later state, but an instant nobody recorded is not recoverable afterwards — and unlike the line-item log §1 defers, this one costs a single column on a write that already happens exactly once, so there is no growth surface to decline.

**`isolated_collateral` is on the row, and this extends the field list #137 inherited.** ADR-0040 §1 fixes paper isolated collateral as the amount moved in **at open** (`notional / leverage`), never topped up; ADR-0041 §6 then classifies it **Tier-1** — mark-independent, and Tier-1 must be "readable even in the recovery window before any mark". It is not recomputable at boot: it is a function of the notional at the instant the position opened, which no other column remembers, and config cannot supply it because ADR-0040 §5's config-authoritative values are leverage and *mode*, not the collateral those produced at a past price. Live re-ingests it each reconcile, but §6's window means the value must read correctly *before* the first reconcile, so it is persisted on both paths. `NULL` distinguishes *cross-margined* from a genuine isolated collateral of `0` on a wiped position.

**(Reinforced by [#142](https://github.com/MarcosACH/tickwright/issues/142); the column stands.** Two supporting claims above were amended at their source and the quotations are updated to match, but the decision is if anything better founded than when it was made.

- The ADR-0041 §6 sentence originally quoted here classified isolated **`margin_used`** as Tier-1. That is now corrected: `margin_used` is Tier-2 in both modes, and only the underlying **`isolated_collateral`** — this column — is Tier-1. Since `margin_used` is no longer persistable *even in principle*, the column is now the **only** durable record of the position's locked collateral, which strengthens the "not recomputable at boot" argument rather than weakening it.
- "Live re-ingests it from `rawUsd`" was wrong on the field: `rawUsd` measured `−103.731933` against a collateral of `25.898067`, being the cash leg net of cost basis. Live recovers the collateral as `marginUsed − unrealizedPnl` (≡ `rawUsd + entry_price · |szi|`). The reconcile still re-ingests it; only the arithmetic changes, and it is the **adapter's** to perform — no schema or recovery-sequence consequence.**)**

**Leverage and margin mode are deliberately absent.** ADR-0040 §5 makes them config-authoritative on both paths, so they are re-read at boot. Persisting them would create a second authority and a second thing for §10 to fail-fast on.

**`entry_price` is nullable** because ADR-0041 §3 keeps a flat-with-history position readable with realized PnL retained, and P1 ([#119](https://github.com/MarcosACH/tickwright/issues/119)) established that a full close resets entry. `NULL` says "no position to have an entry for"; `0` would be indistinguishable from a real price.

**`funding_marks` is the one durable idempotency record in the ledger, and it is keyed by `symbol` because that is the grain of the key it is half of.** ADR-0037 dedupes funding on `(account, symbol, boundary_ts)`, with `account` ambient (ADR-0038) — so within a process the grain is `(symbol, boundary_ts)`, and the durable half belongs at `symbol`. **It is deliberately not a column on `positions`.** A symbol has many position rows — §9 splits one accrual across the owning strategy's row and the unattributed partition's, and a flat row accrues nothing at all (ADR-0037) — so a per-row column would store the same fact many times at the wrong grain, with no single value entitled to answer "has this boundary been applied?". That is the failure §3 already refuses for `account_id` one paragraph up, and here it is not merely redundant: a row created *after* a boundary starts with no mark, so anything reaching back past its creation — live's history read, or a replay rerun — would find nothing to stop it. One row per traded symbol has one value, and the drop test is a lookup rather than an aggregate a reader can get wrong.

**The absence of a row is the "never accrued" state**, which is why `last_funding_ts_ns` is `NOT NULL` — no row for a symbol means no accrual has ever been applied to it, distinct from a boundary applied at epoch `0`. It is an `INTEGER` for the same reason `ts_ns` is: a boundary instant is a timestamp, not money, so ADR-0029's `Decimal`-as-`TEXT` rule does not reach it.

**No Tier-2 value is ever persisted.** ADR-0035 recomputes Tier-2 on every read from `(position, mark)`. A stored `unrealized_pnl` would survive a restart and disagree with the recomputed value the moment a mark lands — a stale valuation with durability, which is worse than no valuation at all.

## 4. The ledger write is one transaction with the order checkpoint

ADR-0035 fixed the *ordering* — store-first, before publish — but not the *atomicity*. A fill mutates the `orders` row (state, `cum_qty`, `applied_event_ids`) **and** the ledger (`positions`, `account`). As two transactions, both orderings are unsound:

- **Checkpoint first, ledger second, crash between.** The order row records `{cloid}:fill:{trade_id}` as applied, so on restart `Order.apply()` treats the redelivered fill as a no-op and **the ledger never receives it**.
- **Ledger first, checkpoint second, crash between.** The order row does not know, so the fill is applied twice and **the ledger double-counts**.

**On live this eventually heals but lies about why**: ADR-0034 reconciles Tier-1 exactly at venue precision, so the first case converges — while raising a divergence alert indistinguishable from a real one. **On paper it never heals at all.** `PaperExchange` persists nothing and holds no position state; after a crash the in-process venue returns empty, so the `Store` is the sole authority for the paper ledger and there is nothing to reconcile against. Atomicity is therefore load-bearing on the default path, not a refinement of the live one.

**(Confirmed verbatim by [#174](https://github.com/MarcosACH/tickwright/issues/174), which needed it.** ADR-0037's funding formula is `− signed_size × price × funding_rate`, and paper *generates* the accrual — so its generator has to know how much is held. This section is what decides where that number comes from: since `PaperExchange` **holds no position state**, it cannot be the venue's own, and the generator reads the **account net size** off the ledger instead (ADR-0034's Σ-invariant, `domain.account_net_size` over `Store.all_positions()`, injected at the composition root).

That is not a concession to the claim above but its consequence, and the slice first got it wrong in a way worth recording: a venue that tallies the net size *it* filled reads correctly for exactly one process lifetime. After a restart the tally is empty while the ledger holds the position, so funding stops — not for the restart gap but **permanently**, since only a fresh fill would refill it; and after a restart *followed by a partial close* the tally holds that close alone, which for a still-open long is the wrong **sign**, crediting funding to a position that owes it. Both are the same defect: a second, unpersisted answer to "how much is held" beside the durable one. The venue keeps the *pricing* — the last tick, the instrument's rate — because that is what a venue is for, and keeps no size at all.**)**

So every ledger mutation is **one `Store` call, one transaction**, covering the order row, the position rows and the account row together (§9).

**Rejected: an explicit transaction scope on the `Store` Protocol** (`with store.transaction(): …` around the existing narrow methods). It cannot be built by wrapping what exists, and the failure mode is silent on the default backend: `sqlite3`'s connection context manager does not nest — an inner `with conn` **commits**, so an exception in the outer block leaves the inner writes durable. Making it sound requires reworking both backends onto savepoint-aware scopes. That is real machinery and a sharp footgun in a codebase whose value proposition is that a reader can believe what they read.

**Rejected: ledger-side durable dedup** (an applied-event set on the position row, making replay idempotent from either crash point). A saga's applied set is bounded by that order's fills and dies with the order; a *position's* set accumulates every fill for the life of the ledger, unbounded — the growth problem §1 declined to take on, reintroduced on the hot row.

The accepted cost is stated plainly: the `Store` Protocol grows a method that knows about three aggregates at once, which the current one-method-per-aggregate shape does not. That coupling is the price of the guarantee, and it is also what keeps §1's deferred audit log addable *inside the same transaction* later.

## 5. Paper skips the restart gap; one bounded per-symbol watermark gates both paths

Two questions look like one and are not. **Which boundaries does the engine produce after a restart?** — a policy question, answered differently by ADR-0037's two ingress paths (paper **generates**, live **ingests**). **Which of them may be applied to the ledger?** — a correctness question, answered identically on both, because both can hand the engine an accrual it has already applied: live through the venue history read it performs by design, paper through a replay rerun, which re-derives every boundary in the file. §5.1 settles the first and §5.2 the second.

### 5.1 Paper: skip the gap, and gate on the same mark

**Paper accrues funding only while the engine is running.** Boundaries that elapse while the process is down are **not** settled on the next start; the loop resumes from the startup instant. **No durable applied-key set exists on either path** — the growing record §4 and §5.2 both refuse.

**"The startup instant" is when the generator's task opens, and [#226](https://github.com/MarcosACH/tickwright/issues/226) moved it one step later.** The loop is now `Exchange.run()`, task-created inside the runner's `TaskGroup` rather than spawned by `PaperExchange.start()` at ADR-0024 step 4 — so it resumes **behind** the startup barrier instead of ahead of it. Under **replay** nothing moves: virtual time does not advance until the feed starts, which is later still. Under **live-wall-clock paper** the skipped gap grows by however long the barrier took — the same policy over a slightly longer window rather than a new one, and the more defensible reading of it, since a boundary settled while reconciliation is still proving the book would price against a position the engine has not finished agreeing on.

**Paper reads the same watermark live does, and the two modes exercise it differently.** Under **live-wall-clock paper** the gate is inert: the generator only ever moves forward from the startup instant, so no accrual it produces can test at or below the mark, and nothing is ever dropped. Under **replay** it is load-bearing, because a replay run genuinely does re-derive past boundaries — `ReplayFeed.start()` iterates the file from the top with no offset or resume, advancing the `ReplayClock` to each row's `ts_event`, so a second run against the same store rewinds virtual time behind the stored ledger and re-crosses every boundary the file spans. Ungated, each of those accruals would apply a second time and the funding line and `cash` would double-count — §5.2's failure reached through the paper generator instead of a venue history read.

**The gate does not touch the skip-the-gap decision, and the distinction is what keeps both true.** The mark gates an accrual on its way *into* the ledger; it does not tell the generator where to resume. Skipping the gap is a statement about which boundaries paper *produces* — the loop resumes from the startup instant, never from the mark — and dropping an already-applied boundary is a statement about which of them are *applied*. On a wall-clock restart the two never meet, which is why the gate is invisible there.

**This makes the paper path idempotent across reruns exactly as fills already are.** `PaperExchange` mints `trade_id` from a per-cloid counter and cloids are deterministic (ADR-0006), so a replayed fill derives the identical `{cloid}:fill:{trade_id}` and the saga's applied set absorbs it. Funding was the one accrual on that path with no equivalent, and the mark supplies it — a replayed run converges on the same ledger rather than compounding one.

ADR-0037's claim that catch-up "needs no stored watermark for correctness — it re-derives the boundary set and the key dedupes" is **confirmed for paper's wall-clock catch-up, and this ADR records both what makes it true and where it stops**. Within a run the in-memory applied-key set dedupes re-fired boundaries. Across a wall-clock restart that set is empty, and the claim survives only because the skip-the-gap policy means nothing re-derives a past boundary to begin with; the crash-immediately-after-a-boundary case is safe for the same reason, that accrual being already durable under §4 with the loop never revisiting it. Had the gap been accrued, a durable watermark would have been **required** on paper too. **Under replay the claim does not hold at all** — re-derivation is the mode's defining behaviour, not a restart edge — so there the watermark is a correctness requirement on paper for the same reason it is on live, just reached by a different route.

**The deciding argument is that there is no defensible price for the gap.** ADR-0037's catch-up is priced by a claim that does not survive a restart:

> "Paper position and the price proxy **only change on feed rows (ticks)**. A virtual-time jump that crosses several boundaries happens *between two consecutive ticks*, where no fill occurred — so position and last-known price are **constant across all caught-up boundaries**."

A restart gap is not between two consecutive ticks. It spans the last tick before shutdown and the first tick after startup, and in live-wall-clock paper the price genuinely moved in between — while `PaperExchange`'s in-memory latest-tick map is empty at the moment catch-up would run, so there is no price at all until the feed delivers one. Every resolution is wrong in a different direction: the stale pre-crash price charges hours of funding at a price known to be out of date; the first post-restart price charges historical boundaries at a future price, unboundedly wrong after long downtime; a persisted last-price column puts a Tier-2 value on disk, which §3 refuses.

**Rejected: accrue the gap.** It is the more faithful reading of ADR-0037's own additive-not-convergent rule, and the rejection is a real trade. The accepted cost: **paper PnL is not restart-invariant** — two runs over the same wall-clock window, one with a restart in the middle, report different funding, and the paper funding line understates by whatever elapsed while down. A stated, bounded fidelity gap is preferable to a restart-invariant number produced by a pricing rule nobody can defend.

**That trade is a live-wall-clock paper concern only, and replay is untouched by it** — the timeline is the file, so there is no wall-clock gap to skip or accrue and the two policies coincide. Replay's exposure is the *other* half of this section: not a gap, but re-derivation, which the mark above gates.

### 5.2 One durable watermark per symbol, required first by live

**Live's ingress genuinely re-delivers, so the same policy does not transfer.** ADR-0037 has live ingesting `userFundings` and reconciling against `userFunding` history "to heal anything that landed while down" — and it lists **live reconcile re-ingest** and **restart-replay** among the three convergence paths the `(account, symbol, boundary_ts)` key is supposed to make no-ops. That key dedupes against an **in-memory** set, which §5.1's restart empties. Nothing else stands between a re-delivered accrual and the ledger: the engine accrues at boundaries `t₁…t₅`, each durable under §4; it crashes; on restart the reconnect's history read and the first reconcile hand back `t₁…t₅` against an empty set, and the funding line and `cash` **double-count**.

That failure is not self-correcting in any way this ADR is willing to accept. Tier-1 heals it against venue truth eventually (ADR-0034), but at the price §4 already refused one section earlier: a divergence alert indistinguishable from a real one, on the money line.

**So the ledger carries `funding_marks` (§3) — one watermark per symbol — and it is the durable half of ADR-0037's key.** An ingested accrual whose `boundary_ts` is at or below its symbol's mark has already been applied and is **dropped**; one above it is applied and advances the mark, inside the same §4 transaction that writes the funding line and moves `cash` — so the mark can never disagree with the sum it guards. The in-memory applied-key set keeps its within-run job unchanged; the watermark is what survives the process.

**The grain is the whole decision, and `symbol` is the only one that holds.** The watermark is the durable half of a `(symbol, boundary_ts)` key, so anything finer stores the same fact in several places and leaves the drop test asking the wrong one. Put it on the position row and the section's own scenario walks straight back in: boundaries `t₁…t₅` apply while only strategy `A` holds BTC, so `A`'s row is marked and no other is; the engine restarts; strategy `B` — or foreign flow into the unattributed partition — opens BTC, creating a row with no mark; the history read re-delivers `t₁…t₅`, every one of them clears the new row's empty mark, and the funding line and `cash` double-count exactly as before. The half-applied case is worse than the fully-applied one: an accrual dropped on `A`'s row but applied on `B`'s still moves `cash` under §4's single transaction, so the ledger records a payment one partition never sees and ADR-0034's Σ-invariant stops holding by construction. Nor can attribution rescue it by charging a re-delivered boundary only to whoever held the position at `t_n` — §1 refuses the event log that would be needed to know who that was. At `symbol` grain none of this arises: one value gates the accrual **before** it is split, and how the amount is then attributed across rows is an accounting question with no bearing on whether it is applied at all.

This is **ADR-0025's per-symbol monotonic gate at accounting grain** — the same instrument `StrategyHost` already applies to ticks. But it is *not* granted the ordering guarantee that gate enjoys, because **Hyperliquid documents none**. The WS subscription is specified only as "Funding payments snapshot followed by funding payments on the hour", with the first message flagged `isSnapshot: true`; the REST `userFunding` read documents `startTime`/`endTime` and a record shape, and neither the docs nor the official Python SDK say anything about the order of what comes back. A gate that assumed ascending delivery and got a batch of `[t₃, t₁, t₂]` would apply `t₃`, then silently **drop two real payments** — an under-count, which is the same class of error in the other direction.

**So the assumption is engineered down to what the venue does promise.** The adapter **sorts each delivered batch by `time` ascending before applying it**, which makes intra-batch order irrelevant — both channels deliver batches, so this is a sort, not a buffer. What remains is only *across*-delivery monotonicity, and that is what the documented behaviour actually gives: the snapshot precedes the hourly stream, and the history read is paginated forward — the info endpoint returns at most **500 elements** for a time range, with the documented idiom being "use the last returned timestamp as the next `startTime`", so pages are consumed oldest-first by construction. §7's store-contract suite is the wrong gate for this one; it belongs in the venue adapter's tests, against a recorded out-of-order batch.

The residual cost is the gate's usual one: an accrual that arrives *below* the mark after a later one has advanced it is dropped rather than applied, and the run under-charges funding. That is now reachable only if Hyperliquid delivers a boundary in a *later* batch than one it already sent — undocumented either way, and with ADR-0034's exact Tier-1 reconcile as the backstop that heals it.

**A watermark, not an applied-key set** — this is the same distinction §4 drew when it rejected ledger-side durable dedup, and it is what keeps ADR-0019's no-processed-event-id-table rule honored rather than excepted. That rule bans a record that **grows with the event stream**: a durable key set accumulates one entry per boundary for the life of the ledger, unbounded in time. `funding_marks` holds one row per traded symbol and overwrites it in place — bounded by the set of symbols the account has ever held, which is the venue's instrument universe, not history. That bound is wider than the configured symbol set, because foreign flow puts positions on the account in symbols this engine never traded (ADR-0038) and live funding arrives for those too; it is still a bound on the *instruments*, which is what the rule is about. It is a third table rather than no table at all, and that is the honest cost of putting the value at its own grain instead of smearing it across rows that already exist. ADR-0037 named a watermark as the instrument available here, having judged it optional for the re-derivation case it was reasoning about.

**One mark, both paths, read and written on the same terms.** Paper's generator advances it as it accrues and tests against it before applying, exactly as live's ingress does (§5.1). The two arguments for this are that the accrual writer needs no `if live:` — one code path settles one accrual, whichever side produced it — and that the read is what makes a replay rerun converge rather than compound (§5.1). Neither argument is about the *schema*: the DDL is unconditional either way (§8), so the only thing a "paper-free" variant would have removed is the argument passed to `checkpoint_ledger` and the lookup before it — and removing the lookup is precisely what leaves replay exposed.

## 6. The restart sequence, and the window that stays open

Ledger recovery slots into ADR-0024's startup order as follows (new steps in bold):

```
bind run_id
→ **account check → seed genesis if absent (paper) → ledger restore**
                                            (§10; before any other recovery work)
→ cache.rebuild()
→ bus.start() → subscribe engine internals
→ startup reconciliation barrier            (+ **live-only account materialisation**)
→ host.start()   — strategies restore, resume seq, subscribe
→ reconcile cadences (incl. the ledger cycle) … feed LAST
```

**The order barrier already performs most of the ledger's recovery.** ADR-0011's barrier reconciles non-terminal orders by cloid and emits synthetic fills; ADR-0035 routes every fill — synthetic included — through the same fill-apply path that writes Tier-1. By the time the barrier clears, the ledger is healed for **everything this engine placed**, including fills that landed while it was down. The residue is foreign flow, venue-side funding accrued while down, and account cash — and ADR-0041 §2 scopes `position()` to the strategy's *own* overlay with the unattributed partition off the seam entirely (§5), so the residue is invisible through `position()` and surfaces only in `account()`.

**The barrier gains one live-only step: materialising the account row.** ADR-0042 §6 creates the live account row at the first reconcile with `genesis_collateral = accountValue − Σ unrealized_pnl`. If that first reconcile were purely a cadence, a live first run would start strategies with **no account row at all** — while ADR-0041 §6 promises `cash` is Tier-1, "never `None`", and "exempt outright, so cold-start is not a blackout". Those cannot both hold. The barrier therefore performs a single `clearinghouseState` read — **unsigned, by address** (R1 [#108](https://github.com/MarcosACH/tickwright/issues/108)), so it needs no signing key — solely to create the row when absent. On paper the step is a no-op: the row already exists by the time the barrier runs, seeded three steps earlier in the check step (below).

**It runs under ADR-0024's existing barrier-failure policy, and does not get one of its own.** Bounded retry with backoff inside the same `startup_reconciliation_timeout` budget, then `FAULTED` and a non-zero exit for the supervisor to restart — the barrier is already the place where a venue read that will not answer stops the engine, so a second read joins that policy rather than inventing a parallel one. **Clearing the barrier with no account row is not an available outcome**: it is exactly the state this step exists to prevent, so a `clearinghouseState` that never answers must fault the process and must never be read as an empty ledger. That is ADR-0011's freeze-don't-guess applied to the account line, and it is what keeps ADR-0041 §6's "`cash` is never `None`" true rather than merely intended. ADR-0024's step 5 and its barrier-failure paragraph are annotated in place accordingly.

**Paper's genesis write lands inside `recover()`, in the same step as the check — not at the barrier, and not later.** `PortfolioProjection.recover()` is **check → seed-if-absent → restore**: the check has just read `account_spec()` (§10) and therefore already holds the operator's declared genesis, and the branch that needs the seed is the one it has just cleared — `load_account()` is `None` and `has_orders()` is `False`, which is exactly §8's refusal condition failing to fire. The row is written there, through the `checkpoint_ledger(account=…)` call §9's taxonomy gives genesis, before `cache.rebuild()` and long before `host.start()`. Writing it later — at the first fill, or on the ledger cadence, which is where ADR-0042 §6 put the *live* twin until this section moved it — would reproduce on the **default** path the failure the barrier step exists to prevent on live: strategies started, `account()` read, and no `cash` at all. What paper does not need is the barrier itself: its genesis is a config value already in hand, so the write cannot fail on connectivity and has nothing to retry, which is the whole of why the two writes sit in different steps. That asymmetry — declared versus ingested — is the same distinction §10's path predicate turns on.

**Rejected: a full ledger reconcile inside the barrier.** It lengthens the gate and — since paper has nothing to reconcile against — gives the two venues different barrier semantics. It also widens the barrier's failure surface in kind, not just in count: the materialisation read is one unconditional existence question with a single retryable outcome, where a reconcile brings divergence classification, healing and the ADR-0040 §6 alert band inside the gate, each with its own way to be indecisive. That the accepted step adds a failure mode too is not the objection — the objection is what a *reconcile's* failure modes would make `StartupReconciliationTimeout` mean. Positions, Tier-1 heals and the divergence alerts stay on the cadence.

**There is no recovery trading-gate. This resolves ADR-0041 §7's deferral.** The decision rests on the residue, not on strategies being inert: the residue is confined to `account()` accuracy, and gating *trading* on a *reporting* surface would breach this map's ceiling, which rules margin enforcement out of scope.

The window is quiet but not empty, and it is worth being exact about which. **No `on_tick` can fire inside it** — `host.start()` runs after the barrier and the feed starts last — so the ordinary trading path is structurally closed. **`on_order_event` can**: strategies subscribe to `OrderEvent` in `StrategyHost.start()`, and the reconcile cadences launch as soon as the start sequence returns, publishing reports that reach the owning strategy as `OrderEvent`s before the first ledger cycle closes the window. A strategy that emits from its order-event handler can therefore place inside the window, reading Tier-1 that ADR-0041 §6 already defines for exactly this state (restored, honest, possibly stale, never a fabricated flat). That is the reading the seam is specified to give, so it needs no gate — but it is a live path, not an impossible one. The window opens at `host.start()` and closes at the first successful ledger reconcile cycle; what is readable inside it is already fixed by ADR-0041 §6 — restored Tier-1, `None` Tier-2 until the first `MarkTick`, freeze-never-flat throughout.

## 7. `Decimal` stays `TEXT` on both backends

Every money column is `TEXT`, written `str(value)` and read `Decimal(text)`, by the same `_records.py` mapping the saga row already uses. The round-trip is exact in representation, not merely in numeric value — trailing zeros (`1.10`), negative zero (`-0`) and exponent forms (`0E-8`, `1E+3`) all survive unchanged, because `str(Decimal)` preserves coefficient and exponent.

**Rejected: `NUMERIC` on Postgres, `TEXT` on SQLite.** SQLite has no exact decimal type (`REAL` is binary float, so it is disqualified outright by ADR-0029), which makes this inherently asymmetric. It would fork the value mapping per backend — exactly what `_records.py` exists to prevent — and `NUMERIC` normalises representation, returning `1000` for `1E+3` and `0.00000000` for `0E-8`: numerically lossless, representationally lossy in a way the `TEXT` path is not.

**Rejected: scaled integers.** They need a per-field scale, and perp sizes, prices and PnL do not share one.

The cost is losing native SQL aggregation on the production-parity backend — no bare `SELECT SUM(realized_pnl)`. The escape hatch is standard (`SUM(realized_pnl::numeric)`), and nothing in the engine needs SQL-side arithmetic: ADR-0034's Σ-invariant is checked in the projection, in memory. **The existing store contract suite is the gate** — it drives one scenario through both backends precisely so that swapping the store changes durability and never behavior, and it grows ledger cases rather than a new mechanism.

## 8. Additive DDL, and an upgraded paper store is refused rather than backfilled

**The migration mechanism already exists and gains nothing.** Both backends apply their DDL at construction out of `CREATE TABLE IF NOT EXISTS`. This change is purely additive — three new tables, no change to `orders`, `strategy_snapshots` or `kill_switch` — so an existing database gains empty tables on next open and that is the entire migration. No schema-version table, no migration framework, no ordering. The Postgres fixture's hardcoded `TRUNCATE` list grows to match, or ledger tests leak state across cases. **(Amended in the implementing slice ([#172](https://github.com/MarcosACH/tickwright/issues/172)): the fixture's list is no longer hardcoded — it is read from `pg_tables` for the current schema, so a new table is truncated the moment it exists.** The obligation this sentence created was the wrong shape: an omission from a transcribed list fails in the one direction nothing catches — rows leak between Postgres cases without any assertion failing, and the always-on SQLite arm cannot notice, because it gets a fresh `tmp_path` per test. Isolation of the arm that only runs under `-m postgres` should not rest on a maintainer remembering to edit a string, and the server already knows the answer.**)**

A version table was **rejected as speculative machinery** for a change that does not need it. The cost is named rather than hidden: the first *non-additive* change will need per-backend handling, because Postgres has `ALTER TABLE … ADD COLUMN IF NOT EXISTS` and SQLite does not.

**The data hazard is paper-only, and it is refused.** An existing paper store carries an `orders` table full of filled orders. After the upgrade it would gain an empty ledger, seed genesis from config, and report a flat account with full cash — silently ignoring every fill it ever recorded. That ledger **cannot** be backfilled: replaying `orders` to rebuild positions is event-sourced recovery through the back door (§1, ADR-0009), and it would not even work, because the per-fill fee only exists on the event as of ADR-0036 and funding did not exist at all — the fee and funding lines would be permanently zero and wrong.

So an `orders` table with rows and **no `account` row** is a startup **refusal** on the paper path, reported by §10's check — `has_orders() and load_account() is None` (§9), gated on the path predicate §10 names — with the same remedy. It converts a silently wrong ledger into a loud failure. On live the same state is legitimate and self-correcting — ADR-0042 §6 creates the row, now at §6's barrier step, and positions heal from venue truth — so the refusal is paper-only, for the same reason atomicity was in §4: no venue to heal from. **The gate is not optional**: applied unconditionally, this condition would fail-fast a live store that predates the ledger, which is a state this ADR calls legitimate one sentence up.

## 9. The `Store` Protocol extension

```python
def checkpoint_ledger(
    self,
    *,
    account: Account,
    positions: Sequence[Position] = (),
    order: Order | None = None,
    funding_mark: tuple[str, int] | None = None,
    ts_ns: int,
) -> None: ...


def all_positions(self) -> list[Position]: ...


def load_account(self) -> Account | None: ...


def funding_mark(self, symbol: str) -> int | None: ...


def has_orders(self) -> bool: ...
```

The write's shape follows from what actually mutates the ledger: a **fill** touches one order, one position and the account; a **funding accrual** touches one or two positions (the owning strategy's and the unattributed partition's), the account and the symbol's watermark, with no order — ADR-0037's "funding has no carrier"; a **reconcile heal** touches many positions and the account, and never the watermark (below); **genesis / live materialisation** touches the account alone. Hence `positions` is a sequence, `order` and `funding_mark` are optional, and `account` is required because every mutation moves cash — ADR-0042 §4's four accruing inputs plus the live-only reconcile correction.

**`funding_mark` is a `(symbol, boundary_ts)` pair on the write, not a field on `Position`**, precisely because §3 keeps the mark off the position row: the advance is a fact about the symbol, and it rides this call rather than a second one so that it lands in the same transaction as the funding line it guards (§5.2). `funding_mark(symbol)` is its read, returning `None` for a symbol with no row — the "never accrued" state §3 encodes as row absence, which admits any boundary, since nothing has been applied to contradict it. It is a scalar read on the accrual path **on both paths** (§5.1), not part of `recover()`'s restore: the mark gates an incoming accrual and is never folded into a reported number.

**A funding correction never rides the heal call, and that is what makes the heal's missing `funding_mark` correct rather than incidental.** §5.2 names ADR-0034's Tier-1 reconcile as the backstop that heals a dropped accrual, and Tier-1 includes the funding line at zero tolerance — so the reconcile *can* move `funding`. It does so as a **keyed `FundingAccrual`**, not as a column correction: ADR-0034 heals through synthetic events rather than blind field overwrites, and ADR-0037 has a reconciler-synthesized funding heal and a venue push of the same boundary collapsing to the same `(account, symbol, boundary_ts)` key. A funding heal therefore re-enters through the accrual path, passes §5.2's gate, and advances the mark inside §4's transaction like any other accrual. Fold it into a heal's `positions`/`account` instead and the mark falls behind the sum it guards, re-opening §5.2's own failure from the other side: the engine is down across `t₆`; it restarts with the mark at `t₅`; the ledger cadence heals `funding` and `cash` up to a venue truth that already contains `t₆`; the `userFundings` snapshot then delivers `t₆`, which tests **above** `t₅`, is applied, and double-counts — with the divergence alert indistinguishable from a real one that §4 and §5.2 both refuse. So the rule is stated rather than implied: **the only write that may advance the mark is the one that applies the accrual, and the only way to correct the funding line is to apply an accrual.**

**Rejected: overloading the existing `checkpoint()`** with optional ledger arguments. It would make every existing order-only call site ambiguous about whether it also writes the ledger.

`load_account()` returning `None` is load-bearing rather than defensive: it is a live first run (materialised in §6's barrier step), it is the paper seed-genesis case (written in §6's check step), and combined with a non-empty `orders` table it is §8's refusal.

**`genesis_ts_ns` takes no argument of its own, because it rides `Account` like its two immutable siblings.** §3's opening instant is the third field of the account row that every write carries and no write moves — `account_id` and `genesis_collateral` are already exactly that — so it needs no parameter here any more than they do. A fill's caller does not invent the value: the aggregate is restored by `recover()` (or built once at genesis) and mutated by `apply()`, so what rides the call is the value the store handed back. The store writes all three on `INSERT` and excludes them from the upsert's update list, which is what §3's "written once, with the row; never updated" means in DDL. **`load_account()` therefore surfaces it**, and that is what keeps §7's shared contract suite the gate rather than a per-backend `SELECT`: the never-updated rule is assertable through the Protocol on both stores — open the ledger at `t₁`, checkpoint a fill at `t₂`, read the account back and find `genesis_ts_ns` still `t₁` while `ts_ns` has moved. A column no read surfaces is one the two backends could disagree about unobserved, which is the one outcome §7 exists to prevent.

**`has_orders()` is the other half of that refusal, and it is a fourth member rather than a reuse of `all_orders()`.** §10 runs the check before `cache.rebuild()`, and `all_orders()` is precisely the mass-read that rebuild performs — answering an existence question with it would deserialize every saga in the store twice on every start, on the recovery path where the engine is least able to afford it. The condition asks whether *any* order history exists, which is `SELECT 1 … LIMIT 1` on both backends. A `bool` also keeps the check honest about what it is entitled to know: nothing about the orders themselves, which belong to the `Cache`'s recovery, not the ledger's.

`all_positions()` returns the unattributed partition **unfiltered**. ADR-0034's Σ-invariant — Σ per-strategy signed size = account net = venue `szi` — holds by construction only if the partition is restored with everything else, so filtering belongs at the `Portfolio` seam (ADR-0041 §5 keeps it off the strategy API) and never in the store. That also keeps the partition visible on `PortfolioProjection`'s concrete surface, which ADR-0041 §8 reserves for telemetry and CLI.

## 10. The check: where it runs, what it reads, what it raises

The startup check runs **first, immediately after the run correlation is bound and before any other recovery work** — ADR-0042 §3's placement, now concrete: `Engine._start_sequence` calls `PortfolioProjection.recover()`, which performs check → seed-genesis-if-absent (paper, §6) → restore. The runner keeps the ordering (its module docstring is explicit that lifecycle knowledge lives there rather than smeared across components); the projection keeps the ledger logic.

**`AccountSpec` gains `genesis_collateral: Decimal | None`** — paper declares the operator's value, live reports `None`. This is how the configured genesis reaches a check that must not read config: ADR-0042 §1 makes the `case "paper":` arm of `build.py` the single reader of `config.paper`, and that arm hands the value to `PaperExchange`, which surfaces it through the `account_spec()` accessor ADR-0038 already defines. The check then compares two objects the engine already holds — the stored row and `exchange.account_spec()`. Live's `None` is not a gap but ADR-0042 §6's rule that on live the value is "provenance only — nothing cross-checks it, because there is no configured counterpart to check against".

This is a different call from ADR-0042 §2's refusal of a collateral-*currency* field on `AccountSpec`, and the distinction is load-bearing: that was refused as a seam with one implementation (one possible value, USDC). Genesis has two genuinely different implementations — paper declares, live ingests — and ADR-0038 defines `AccountSpec` as the venue-declared account facts, which is what an account's opening value is.

**One error type**, `StoreAccountMismatch` (an `InvariantViolation`, ADR-0042 §3), covering two disjoint conditions — they cannot both fire, since a missing row leaves no fields to compare:

- **Fields disagree.** The account row exists and what the adapter declares disagrees with it. `account_id` compares on **both** paths. `genesis_collateral` compares **only when the adapter declares one** — `account_spec().genesis_collateral is not None`, the same predicate the second condition uses — because a `None` declaration is *no counterpart to check against*, not a disagreement. Every disagreeing field is named at once (ADR-0042 §3), so an operator who changed both learns both on the first restart.
- **No ledger for existing history.** `orders` has rows and there is no `account` row — **on the paper path only**, which the check reads as `exchange.account_spec().genesis_collateral is not None` (§8).

**That predicate is the decision, not an implementation detail, and it gates both conditions.** The check must know which path it is on, and it is entitled to exactly one venue-declared object: `account_spec()`. Genesis is `None` precisely when the account's opening value is *ingested* rather than *declared*, which is the same fact as "this path has a venue to heal from" — so the field already carries the distinction both conditions turn on, and no venue-kind flag needs inventing to sit beside it. Each condition gets it wrong in a way the operator feels, and in opposite directions. Ungated, the second refuses a live store predating the ledger instead of healing it. Ungated, the **first** is worse: live's stored genesis is `accountValue − Σ unrealized_pnl` (ADR-0042 §6) while its declared genesis is `None`, so the two always differ and **every live restart after the first fail-fasts** — a check whose whole purpose is to catch a swapped account bricking the path it was never meant to police. ADR-0042 §6 already states the rule ("§3's fail-fast is inherently paper-only; ADR-0038's `account_id` check applies on both paths"); this bullet is where it becomes a condition rather than a remark.

A second exception class was rejected: the operator's remedy is the same sentence either way — point the run at a fresh store, or restore the declared values — and a distinct name would buy precision nobody acts on differently.

## Consequences

- **ADR-0019's "what the store holds (minimal)" list gains a fourth, fifth and sixth entry**: the position ledger, the single account row and the per-symbol funding watermarks. Its no-processed-event-id-table rule is *honored* rather than excepted — the rule bans a record that grows with the event stream, and `funding_marks` holds one overwritten row per traded symbol, bounded by the symbols the account has ever held rather than by history (§5.2) — and §4 makes the order saga's applied set authoritative for the ledger too, by atomicity.
- **ADR-0024's startup sequence gains a step, and its barrier gains a sub-step** (§6), both annotated in place. The ledger check-and-restore lands between step 1 and step 2 — ahead of the `Cache` rebuild, because it can refuse the store outright and because its existence question is a narrow `has_orders()` rather than the mass read step 2 performs. That step is also where **paper** seeds its genesis row, since its opening value is declared rather than ingested and the check is already holding it. Step 5's barrier performs the **live-only** account materialisation, under the **existing** barrier-failure policy rather than a new one: bounded retry, then `FAULTED`, and never a cleared barrier with no account row. Both writes land before `host.start()`, which is what makes ADR-0041 §6's "`cash` is never `None`" true on either path.
- **ADR-0035's Tier-1 write is now atomic, not merely ordered.** "Store-first, then project, before publish" stands; §4 adds that the store step is one transaction spanning the order row and the ledger rows.
- **ADR-0037 is split by mode, not simply confirmed.** Its no-watermark claim holds for **paper's wall-clock catch-up** — §5.1 records that the skip-the-gap policy is what makes it hold across a restart, and that accruing the gap would have made a durable watermark mandatory there too. It does **not** survive on **live**, whose ingress re-delivers history, nor under **replay**, which re-derives every boundary in the file on every run (`ReplayFeed` restarts from the top). So a per-symbol `funding_marks` row is the durable half of ADR-0037's idempotency key (§5.2) and is read on **both** paths — at `symbol` grain, because that is the grain of the key, and a mark on the position row would leave a row younger than a boundary unable to reject it. Its "all three convergence paths are no-ops" claim is true of restart-replay only because of that row. **The venue guarantees no delivery order** on either funding channel, so the adapter sorts each batch by `time` before applying — a watermark is only as safe as the ordering it is fed. A new documented paper limitation: funding is not restart-invariant across a wall-clock gap (it understates); a *replay* rerun, by contrast, now converges.
- **ADR-0038's `AccountSpec` gains `genesis_collateral`** (§10), and invariant #7's store binding gains its second condition (§8). Its "`account_id` is stamped on durable ledger rows" is **narrowed to the single account row** (§3) — position rows carry no copy, because a second place to write the binding is a second place for it to disagree with the one §10 checks.
- **The `Store` Protocol gains five members**, not three: `checkpoint_ledger`, `all_positions`, `load_account`, `funding_mark` and `has_orders` (§9). **(Six landed in the implementing slice ([#172](https://github.com/MarcosACH/tickwright/issues/172)):** the ledger five decided here, plus **`history`**, promoted from adapter surface to the Protocol — an orthogonal correction rather than a widening of this ADR's extension, made here because this is the slice that touched the seam. See §1's amendment for why.**)** `funding_mark` reads the per-symbol watermark on the accrual path; `has_orders` exists so §8's refusal can ask an existence question without running the recovery mass-read a second time before `cache.rebuild()`. The watermark is advanced by **exactly one** write — the one that applies the accrual — so a Tier-1 funding correction must re-enter as a keyed `FundingAccrual` (ADR-0034's heal-through-events, ADR-0037's shared key) and never as a column fix on the reconcile heal (§9).
- **ADR-0041 §7's deferred recovery trading-gate is resolved: there is none** (§6). §6's nullability rules are unchanged and now have a concrete window to describe.
- **ADR-0042's check is extended in place** — same error type, same remedy, one further condition — and **both** conditions are gated on `AccountSpec.genesis_collateral is not None` (§10): the new one so it never refuses a live store where that state is legitimate, and the inherited field comparison so a live `None` declaration is read as *nothing to check against* rather than a mismatch against the row ADR-0042 §6 tells live to write. Its `NOT NULL`-only genesis column is honored exactly, and §3 adds `genesis_ts_ns` so §6's "when did this ledger open, and at what value" is answered in full rather than by half — carried on `Account` beside the two fields that already never move, and surfaced by `load_account()` so the never-updated rule is gated by the shared contract suite rather than by per-backend SQL (§9). Its §6 live materialisation is **narrowed** in place from "the first reconcile" to the startup barrier (§6), the formula unchanged; paper's genesis write is placed in the check step for the same reason, one step earlier because it needs no venue read.
- **`strategy_id` becomes constrained for the first time**: a validator on `StrategyConfig` and `StrategyHost.register` rejecting `__unattributed__` (§2). Existing configured strategies are unaffected unless one holds that literal.
- **A ledger line-item audit log is a named, deferred extension point** with a stated cost (§1): additive whenever taken, but never retroactive.
- **The first non-additive schema change will need per-backend DDL handling** (§8) — the accepted cost of declining a version table now.
- **Implementation is downstream.** This ADR fixes the schema, the cadence, the restart sequence and the Protocol shape; the slices that build them belong to the map's PRD, not to this ticket.
